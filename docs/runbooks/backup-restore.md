# Backup and restore

Daily physical PostgreSQL17 backups use `ops/backup/backup.sh`: `pg_basebackup --wal-method=stream`, `pg_verifybackup` (including WAL), tar, then authenticated AES-256-GCM. Never pass credentials in argv. Supply private `PGSERVICEFILE`/`PGPASSFILE`, `BACKUP_ROOT` (absolute private mounted backup directory), and `BACKUP_KEY_FILE` (absolute mode0600 file containing32 random bytes). Generate the key offline, escrow separately, never commit it. The backup account needs replication privilege and approved source access; runtime roles cannot back up. Reject nonempty `postgresql.auto.conf`; provision configuration separately.

Each atomic backup directory contains only `base.enc` and `manifest.json`: snapshot upper bound, WAL timeline/start/end, encrypted SHA256 and PostgreSQL manifest SHA256. GCM authenticates ciphertext; the outer manifest's snapshot/WAL must be crosschecked with the authenticated inner manifest before use. Restrict directory mode0700. Retain backups35days only after verifying a newer backup and monthly restore drill; no automatic destructive retention is provided.

Configure PostgreSQL `wal_level=replica`, `archive_mode=on`, `archive_timeout=60s` and `archive_command='/opt/echo/ops/backup/archive-wal.sh "%p" "%f"'`. Its `WAL_ARCHIVE_ROOT` must be a distinct approved Russian storage mount, protected from source-host loss. Encrypt every completed segment with the same escrowed key. Segment, timeline .history and backup .backup filenames are validated against PostgreSQL shapes; path traversal fails. A completed encrypted file is fsynced before rename and the containing directory is fsynced before archive success. An existing file is decrypted, compared and resynced on retry; differing content fails. Storage must honor durable fsync semantics. Monitor `pg_stat_archiver` failures and last archived time; alert before the5minute RPO budget. Never claim healthy backup from a successful command alone: verified manifest and monthly isolated restoration are mandatory.

PostgreSQL documentation: [physical backup](https://www.postgresql.org/docs/17/app-pgbasebackup.html), [continuous WAL archiving](https://www.postgresql.org/docs/17/continuous-archiving.html). This repository provides tooling and local drill evidence; approved storage geography, escrow, continuous production archiving and ongoing monthly drills require deployment evidence.

Monthly isolated drill: `npx vitest run tests/functional/operations/isolated-restore-drill.test.ts`. It creates and removes two PostgreSQL17 containers, takes an encrypted physical backup, verifies/decrypts it, restores into a separate cluster, fences/reconciles/reopens, and asserts no old delivery eligibility. Capture RPO≤300000ms, RTO≤14400000ms and checksum results; this local drill does not prove deployed second-storage availability.

`ops/restore/prepare-restore.sh BACKUP_DIRECTORY` needs an absolute NEW isolated parent via `RESTORE_ISOLATED_ROOT`; it refuses an existing pgdata, authenticates the archive, matches the inner snapshot/WAL manifest, checks PostgreSQL data/WAL, disables source archiving/listener and writes `restore.env` with `RESTORE_FENCE=on`. It does not start a DB. Start the isolated cluster on a private network, with all runtime processes stopped/fenced. Set `system_state.restore_fence=true` as offline migrator before starting any runtime. Verify migration checksums/invariants, then preview:

```
node --experimental-strip-types ops/restore/reconcile-restored-state.ts --incident-id UUID --snapshot-at ISO
```

Only add `--apply` after preview. It records an anonymous restore incident, quarantines pending/sending/retry created≤snapshot as `uncertain_restore`, invalidates delivery/conversation leases and increments deployment epoch. Replies materialized later from an old inbound are also quarantined. Applied incident retries are idempotent and reject a different snapshot. Check subscription using the test bot/offline provider checklist and verify no old runnable delivery. Explicit `--apply --reopen` opens the database fence; change runtime `RESTORE_FENCE=off` only after approval of the restore report. Never reopen automatically. Restore credentials use offline `DATABASE_URL_MIGRATIONS` with username echo_migrator, never runtime grants. Future Task Domain reconciliation is outside Stage1.

Runtime deployment: build `docker build -f deploy/Dockerfile -t echo-max:stage1 .`, provision the private Docker network `echo-max` and external PostgreSQL17, then install the four `deploy/systemd` units. Each mode0600 `/etc/echo-max/ROLE.env` contains only its own `DATABASE_URL_ROLE`, required MAX configuration, `RESTORE_FENCE`, and explicit `FOUNDATION_ECHO_ENABLED=true` production opt-in. Omit migration credentials from every runtime. Migrator runs separately and offline. Units run the same image as UID1000, with read-only root, a bounded /tmp, no capabilities, private network and65second drain before kill. Gateway is published only to loopback. Include `deploy/nginx/echo-max.conf` inside an operator-provisioned TLS server; /ops stays private. Set and validate scheduler secret version before reopening. Signals finish active bounded work and close pools; shutdown failure exits nonzero.


Archived-WAL PITR: supply `RESTORE_WAL_ARCHIVE_ROOT` (absolute private second-storage archive with .enc segment/history files) and `RESTORE_TARGET_NAME` (explicit pre-created PostgreSQL restore point, restricted identifier). Preparation authenticates/decrypts every archived file into the isolated target, adds recovery.signal and a restore_command, then promotes only at that named target. An unreachable target must fail recovery; do not remove it to silently accept an older base backup. Base-only mode is explicit when both variables are absent and cannot establish post-base RPO. After target recovery, verify an acknowledged source marker and use the verified recovery-point timestamp as --snapshot-at, not the old base stamp. Reconciliation rejects a cutoff older than restored inbound/outbound records, preventing partial quarantine after PITR. Keep all runtimes off until the DB fence is set.

The physical drill now archives a post-base acknowledged marker, encrypts its WAL, performs named-target recovery and checks the marker survives. RPO is the difference between acknowledged source and recovered marker timestamps (zero in this controlled drill), not age of backup-command completion; RTO includes backup, archiving, decryption, PostgreSQL recovery, quarantine and checks. Local test mount does not establish second-storage failure independence or geography.
